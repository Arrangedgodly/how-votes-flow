## T2 — Counting engine (pure TS) + unit tests (2026-08-28)

- Owner: FE · Status: awaiting-approval
- Outcome: deterministic single-winner instant-runoff engine in `src/engine/`, pure TypeScript (no React imports, no DOM). Input: candidates (generic `Candidate` — id + type-open display info) and weighted ballot blocs (positive-integer weight, ranking of known ids, no duplicates). Output: full round-by-round `CountResult` — per-round tallies per continuing candidate (candidate order, zero-vote lanes included), active/exhausted/total accounting plus per-round majority threshold, eliminations with per-destination transfer counts and newly-exhausted counts (UI can animate exactly N votes from X to each Y), deterministic tie-break events, winner declaration with method/flag.

### Changed files

- `src/engine/types.ts` — full type model: `Candidate` (generic for type-open display info), `BallotBloc`, `ElectionInput`, `CountRules`/`MajorityDenominator` (parameterizable rules), `RoundResult`/`RoundTally`, `Elimination`/`Transfer`, `TieBreakEvent` (+ `TieBreakPurpose`, `TieBreakResolution`), `WinnerDeclaration` (+ `WinnerMethod`), `CountResult`.
- `src/engine/rules.ts` — domain rules isolated here per plan: `defaultCountRules` (majority denominator 'active'; final-two leader rule on), `votesNeeded` (smallest count past half the denominator), `resolveTieBreak` (fewest first-round votes loses, then stable candidate-order fallback; `resolvedBy` names the rule that made the outcome unique). R1 contradiction = localized change to defaults, API/round model untouched.
- `src/engine/count.ts` — `runInstantRunoff(input, overrides?)`: validation, then per-round decision order: (1) majority of denominator wins outright; (2) final two with no majority → leader wins flagged (`wonWithoutMajority: true`, method 'final-two-leader'; exact tie resolved by the same cascade, disclosed on the winner); (3) else eliminate fewest (tie-break if tied) with per-destination transfers + exhaustion. Ballots count toward highest-ranked continuing candidate — stateless per round, no hidden carry-over. Round bound = candidates+1 as a termination bug guard.
- `src/engine/index.ts` — barrel export.
- `src/engine/count.test.ts` — 17 tests (9 behavioral, 8 validation).

### Decisions / deviations

- **Final-two rule under the active denominator:** with exactly two continuing candidates, no majority ⟺ exact tie (leader of two always holds >half of active otherwise). So under the adopted default the flag fires via the tie-break cascade (survivor declared leader, event disclosed). The non-vacuous "leader below half" case exists under `majorityDenominator: 'total'`, which is implemented behind the same code path and covered by a test. Both semantics documented in `count.ts`/`rules.ts` headers — if R1 contradicts the default, flipping `defaultCountRules.majorityDenominator` is the whole fix.
- **Tie-break cascade direction:** first in stable candidate order LOSES (consistent for elimination and final-winner purposes). `resolvedBy` records the rule that made the outcome unique ('first-round' vs 'candidate-order').
- **Engine is size-agnostic:** no hardcoded 4 candidates / 3 ranks / 100 votes — validation enforces ≥2 candidates, ranking length ≤ candidate count, positive integer weights. The 100-vote constraint stays a scenario-layer (T3/T7) concern; tests use 100.
- **Zero-transfer survivors omitted** from `elimination.transfers` (non-zero streams only) — documented in types.ts; UI treats absence as 0.
- **Round-1 plurality leader intentionally not computed by the engine** — the verdict card (T8) and recipe tests (T3) derive it from `rounds[0].tallies`, avoiding a second tie policy in the engine.
- Test-data arithmetic bugs during authoring (two scenarios initially summed to 115 / had wrong minimum) were caught by the tests themselves and fixed — evidence the invariants do real work.

### The recorded model — the conserved electorate

Exactly 100 voters exist; every one is on a bloc or in the free pool; `placed + pool === 100` is the invariant every action preserves. Steppers move one voter at a time (up draws from the pool — blocked at pool 0, so the placed sum can never exceed 100; down returns one, floor 1). Typed weights parse-and-clamp into [1, weight + pool]. Deleting a bloc returns all its votes to the pool; adding one takes a single unplaced vote (needs pool ≥ 1, roster cap 12). "Spread the unplaced" is the balance control: largest-remainder distribution of the whole pool across blocs — the one-click way back to a full field. TIP OFF is gated on `lineupIssues(...) === []`: all 100 placed AND structurally engine-valid (the structural half holds by construction; the gate checks honestly). "Sum never ≠ 100" reads as: the run never sees ≠ 100, and the 100 never leave the board — an unplaced remainder is a blocked state with the recovery stated, not a corrupt one.
